# Calculator attribute criteria

Review the bug details, profiles, and comments to assess:
- *Platforms* (`--platforms`) The platforms where the bug is known to occur. That normally includes the platform the reporter hit it on, taken from what they describe (their user agent, OS, or device), not from the OS / Platform field, which is often left at a single-OS default. Add other platforms only when someone reports or reproduces it there, or the cause is clearly platform-independent. The exception is when the OS / Platform field itself reads `All`: that value is never a default (a default is a specific OS, typically Windows) and requires someone to have deliberately selected it, so treat it as a genuine signal the bug applies across platforms. When the bug gives no platform information at all, use all three desktop platforms (`windows macos linux`) for a desktop bug, or `android` for a mobile (Fenix/GeckoView) bug; don't leave it empty.
- *Resource impact* Only specify if resource use is a PRIMARY concern, not a side-effect — the bug has to be primarily *about* high resource use, not merely result in it. A total hang is not by itself evidence of severe resource use: a hang can be a deadlock with no severe resource use involved. Only score severe resource impact when the severe resource use is understood (stated or clearly implied) to be the *cause* of the hang/slowdown, not just a coincident symptom.
- *Configuration* Can refer to uncommon hardware, uncommon feature usage, or unusual browser state (hundreds of tabs, long runtime, etc.). Baseline test: if a device reproduces the issue in its default configuration with standard peripherals, that's `general`. A non-default requirement — uncommon hardware (e.g. a high-refresh-rate display, when most screens are still 60fps), a non-default setting (e.g. a native darkmode not everyone enables), an extension, a specific input device — pushes it off `general` toward `common`/`rare` depending on how widespread that requirement is. Some non-default settings are trending toward ubiquitous (e.g. darkmode) without being there yet; don't round those up to `general` early.
- *Reproducible locally* (`--reproducible`) Refers to engineers/agents having been able to reproduce. STR or the reporter reproducing is not relevant — this holds even when the reporter has an @mozilla.com address and is QA or an engineer: filing the bug by following their own STR is still the reporter reproducing, not a separate confirmation. This flag is strictly for whether an engineer or QA has indicated they can reproduce the bug locally. The @mozilla.com rule below applies only to someone other than the reporter. Three states, and the distinction between the last two matters:
  - `reproduced` — an engineer or QA other than the reporter says they reproduced it locally. If a user with an @mozilla.com address who is not the reporter has reproduced it, treat that as reproduced.
  - `not-reproduced` — an engineer or QA says they **tried and could not** reproduce it. This requires positive evidence of a failed attempt, not merely the absence of a confirmation.
  - `not-attempted` (default) — nobody has said either way. Use this whenever the bug is silent on reproduction; do NOT infer `not-reproduced` from silence. An automated attempt (e.g. an `[autowebcompat:repro-failed]` whiteboard tag) is not an engineer or QA attempt; with no human attempt, use `not-attempted`.
- *Multiple reporters* (`--multiple-reporters`) Means **multiple people independently hit and reported the bug**, e.g. duplicate bugs filed against it, several commenters saying they see it too on their own machines, or a bug filed on behalf of many users. It is NOT "a bunch of people commented on the bug" — a long discussion among engineers, triagers, or a single reporter going back and forth is still one reporter. It is also NOT an engineer confirming they can reproduce it; that is `--reproducible reproduced` and nothing more. Do not set this flag on the strength of comment volume alone; if you cannot point to distinct people independently encountering the bug, leave it off.
- *Multiple sites* (`--multiple-sites`) The same root cause reported on multiple sites, typically across separate bugs. Several hostnames mentioned inside one report is not enough.
- *Websites affected* (`--pages-affected`) Not a count of sites named in the bug — a measure of how popular/high-traffic the affected site(s) are, i.e. how much of our user population would notice if this site had a problem. Do not estimate this from your own sense of a site's popularity: look it up from real Firefox pageload traffic with the calculator located in Step 0, passing the affected host exactly as the bug gives it (a URL is fine) and the same platforms you chose for `--platforms`:

  ```
  python <calculator path from Step 0> --classify-domain <host-or-url> --platforms <platforms...>
  ```

  It prints the tier to use (`major` = top 50 by Firefox pageloads, `common` = 51–5000, `rare` = beyond 5000 or unranked) and the rank behind it. Use that tier; do not read or search the data file it uses. The tier is about the site's overall reach, not the reported feature's — a rarely-used map layer or an ad iframe on a `major` site is still `major`. When the bug names several affected sites, look up each and use the highest tier. The data records the domain a page actually loaded from, so a site that has moved or redirects to another domain (e.g. `twitter.com` to `x.com`, `vk.com` to `vk.ru`) comes back unranked under its old name: when you know the site's current domain, look that up too and use the higher tier. When the affected site is a customer subdomain of a shared hosting or app platform (e.g. `*.vercel.app`, `*.github.io`, `*.netlify.app`, `*.blogspot.com`), the lookup falls back to the platform's own traffic, which says nothing about that one site: use `rare` unless the lookup ranks the full subdomain itself. When the bug names no specific site but it is clear the problem affects browsing everywhere — page loads or navigation on any site, not just some pages (e.g. every navigation after a cold start, network requests failing for all pages) — use `major`. A browser-level freeze or chrome jank is not this: it is scored by `--browser-impact`, so leave it `unclear` unless page loads or navigation themselves fail or slow on every site. Otherwise, when no specific site is identified (e.g. "some websites", a browser UI issue), use `unclear`; it scores the same as `common` (×1) but records that the input was unknown rather than assessed. This is independent of `--multiple-sites`, which is about whether the same root cause recurs across more than one site, not how popular any one of them is.
- *Page load impact* (`--pageload-impact`) Strictly about delay during the page's own initial load or navigation — not post-load interaction, scrolling, or resource-usage jank, even when the bug's text happens to contain the word "load" or "navigate" in an unrelated sense.
  - `none` (default) — no reported load/navigation delay, or the complaint is about something after the page has already loaded.
  - `some` — a load/navigation delay reported as a small, specific relative difference (e.g. "10% slower", "100-200ms slower than Chrome").
  - `severe` — a load/navigation delay that is large, open-ended, or unbounded (multiple seconds or more, "very slow", "frequent long janks" on load, no numeric bound given beyond "slow").

  Leave it at `none` when the delay is a clear downstream symptom of a different primary cause that is already scored elsewhere (e.g. pages hanging specifically because another process is saturating the CPU, scored under `--configuration` instead) — scoring it again under page load impact double-counts the same root cause.
- *Animation* Only for web-driven animated content, NOT browser UI (scrolling, resizing, tab switches). The test is whether work *driving the animation itself* is responsible for the perceived lack of smoothness — e.g. significant time in Canvas/Graphics layers doing the drawing for that animation — not whether an animation is merely on-screen while something else janks. If a profile shows the main thread janked by JavaScript with no indication the animation's own rendering work is the bottleneck, that's not `--animation`, even if an animation is visually present.
- *Impact on browser* (`--browser-impact`) This is strictly for when the browser's own UI/process is affected — chrome (tab bar, menus, other tabs, the whole application), not a symptom scoped to one site's content. A site being slow, laggy, or janky to scroll/interact with is `--site-impact`, even when the cause is CPU-heavy or GPU-heavy rendering work, UNLESS that work spills over into genuinely freezing or crashing the whole browser (every tab, not just the one with the offending page) — in that case it is `browser_impact`, and `site_impact` stays at its default (`minor`) to avoid double-counting the same event twice. Five categories, not a severity ladder — pick the one that names what actually happened, not a tier on a scale:
  - `minor` (default) — no browser-level impact; any slowness is confined to a single site's content/tab.
  - `startup` — anything slowed because the browser is completely cold: app launch itself, and also work the first use after a cold start pays for (e.g. quota or storage initialization delaying the first navigation). Use `startup` rather than page load impact for such a delay even when it shows up as a slower first page load. A page that loads slowly inside an already-warm browser is not `startup`.
  - `shutdown` — the browser's own close/exit is slowed (hangs or delays when quitting, not a page unloading).
  - `jank` — the browser's own chrome UI (tab bar, menus, address bar — not page content) is sluggish, or briefly (on the order of a few seconds) stops responding across the whole UI, while the browser keeps running and recovers on its own — stuttery tab switching, laggy menus, a short "all tabs unresponsive for 1-5s" episode. This covers a real whole-UI freeze when it is brief and self-recovering, not just chrome being slow to redraw. When a profile or an engineer shows the stall is in the parent process (where the browser's own UI runs), it is browser-level — usually `jank` — even when a page triggered it and the reporter describes only that page stuttering; leave `site_impact` at `minor` for it.
  - `major` — the whole browser stops responding for a sustained period, or crashes/is killed, not just the offending tab or site. The difference from `jank` is duration/severity, not just "more than one tab affected": a several-seconds-and-recovers full-UI freeze is `jank`; something sustained enough to need killing the app, or an actual crash, is `major`. A full-browser freeze/crash is `major` even when a single tab's content triggered it — the deciding question is whether other tabs/the whole app were taken down too, not where the problem originated. But read past the reporter's own wording rather than pattern-matching on alarming phrases: "froze the whole browser" or "Firefox crashed" is often imprecise for a per-tab event — e.g. the "this tab isn't responding" recovery dialog for one unresponsive tab is a site/tab-scoped event (`site_impact`, not `major`), not every tab freezing. Likewise a memory spike that the report itself says is released shortly afterward, with an OOM kill mentioned as an occasional/worst-case outcome rather than the typical result, is `resource_impact`, not `major`. And a report that Firefox can't load pages or make network requests while something *external* (another process, the OS) is hogging CPU is not automatically `major` either — if the browser's own chrome (menus, tab switching) isn't described as unresponsive, this is a networking/pageload symptom of outside resource contention, not browser_impact at all.
- *Impact on site*
  - `minor` (default) — a slowdown or jank a user could easily miss or shrug off: barely perceptible, or perceptible but not disruptive to what they're doing.
  - `noticeable` — degraded but still interactive: laggy scrolling, low frame rate, a page that feels slower or janky throughout, but the user can keep working with it the whole time. Also use `noticeable` for a measured, repeatable slowdown where Firefox is measurably worse than another browser on the same task (e.g. a call taking several ms longer, uploads markedly slower than in Edge), even if a user might not feel it in the moment; `minor` is for slowdowns that are neither felt nor measurably worse than another browser.
  - `major` — the page stops responding entirely for a span of multiple seconds or more (blank screen, frozen UI, input not registering, "stuck") before recovering, rather than merely being slow or janky the whole time. This tier needs the freeze to also be frequent enough to define the experience of using the site — recurring roughly every couple of minutes or less, not a one-off in a longer session. A report of a single or rare multi-second freeze is `noticeable`, not `major`, even though the freeze itself is multi-second; it's the combination of multi-second AND frequent that earns `major`. The calculator has no separate frequency field, so this tier is where that distinction has to live. A site is also `major` if it is janked so severely a user cannot get anything done on it at all, or a page never finishes loading (stuck indefinitely, not merely slow); in the latter case leave page load impact at its default, to avoid double-counting.

  When the whole browser hangs or freezes, use `--site-impact minor`: the hang is scored by browser impact, and counting it again for the site double-counts it.
- *Reproduces in Chrome* (`--chrome`) Set only when someone reports that Chrome shows the same problem to a comparable degree — e.g. Chrome also hangs for minutes on the same page. If Chrome is better, leave it off, including when Chrome is also somewhat slow but noticeably less so ("Chrome was slower as well but not that slow" means off: the gap is the Firefox bug). A report that Chrome is fine or faster means off. Silence means off. Use the most recent comparison: if a later comment reports Chrome now shows the problem too, that overrides an earlier "Chrome is fine".
